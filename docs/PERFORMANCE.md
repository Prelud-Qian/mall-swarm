# 压测与验证报告

本文件记录 mall-swarm 各优化功能的实测数据：压测方法、结果、结论。所有测试在本地开发环境完成（MySQL/Redis/RabbitMQ/ES 部署于 192.168.88.129，应用服务本机运行，JDK 17）。

并发压测工具：`xargs -P` + curl（N 个并发请求）；SQL 计数通过 MyBatis DEBUG 日志统计；Redis/ES/MySQL 状态通过 redis-cli / ES REST API / mysql 客户端直接查询对账。

## 1. 秒杀下单闭环

**场景**：秒杀商品 10 件库存、每人限购临时放宽到 100（压测用），100 个并发请求同时抢购。

**结果**（三轮独立压测，结果完全一致）：

```
每轮：成功 10 单 / 已抢完 90 单 / 总响应 100
Redis 秒杀库存：10 → 0（无负值，Lua 原子扣减）
数据库秒杀订单：每轮 +10（与成功数一致）
SKU 锁定库存 lock_stock：每轮 +10（每单锁 1 件）
```

**对账结论**：成功数 == 库存扣减数 == 新增订单数 == 新增锁定数，四层数据完全一致，零超卖。

**超时关单**：flashOrderOvertime 配置 60 分钟。实测 21 个未支付秒杀订单在超时后全部自动取消（status=4），锁定库存全部释放（lock_stock 21→0），验证 RabbitMQ 延时关单链路（TTL + 死信转发 + 幂等取消）。

## 2. 商品详情缓存三兄弟

**场景**：商品详情接口（缓存 miss 时回源 7+ 次 DB 查询），三轮测试 + 一次重启，结果一致。

| 测试 | 方法 | 结果 |
| --- | --- | --- |
| 缓存命中 | 首次请求后立即二次请求 | 首查 7+ 条 SQL 回源并写缓存；二查 0 条 SQL |
| 防雪崩（随机过期） | 查看缓存 key 的 TTL | TTL=1884s，落在 1800~2100s（30分钟+随机84秒）区间 |
| 防穿透（空值缓存） | 请求不存在的商品 id | 首次写入空值缓存 "NULL"（TTL=300s）；连打 3 次 0 回源 |
| 防击穿（互斥锁） | DEL 缓存后 20 并发 | pms_product 回源查询恰好 1 次，其余 19 个经互斥锁等待后命中缓存 |
| 缓存一致性 | admin 逻辑删除商品后查 TTL | 缓存 key 立即被删（TTL=-2） |

**结论**：击穿场景下"全系统同时只有一个线程回源"实测成立——互斥锁 + 双重检查将 DB 压力与并发数解耦。

## 3. 商品详情 CompletableFuture 异步编排

**场景**：缓存 miss 回源路径，8 次 DB 查询从串行改为异步编排（1 串行根 + 6 路并行 + 1 路二级依赖）。

**结果**：同一次回源请求的 SQL 日志显示 5 个不同线程同时执行（`nio-8085-exec-4` 跑根查询，`businessPool-1/2/3/6/7` 各跑一路）；回源耗时 356ms（串行时约为 8 次查询耗时之和）。

**结论**：并行编排生效（日志线程名证实），回源耗时降为"最长一路 + 根查询"。与缓存三兄弟配合：缓存命中（0 SQL）→ miss 后互斥锁唯一回源 → 回源内部并行，三层递进缩短链路。

## 4. Sentinel 限流与熔断

**限流（portal 商品详情）**：QPS 阈值 5。30 并发压测：通过 8、拦截 22（返回"系统繁忙"）。通过数略高于 5 为并发请求毫秒级先后跨统计窗口所致，属正常。

**熔断（portal 秒杀接口）**：异常比例 50%、最小请求数 2、熔断时长 10 秒。实测完整状态机：

```
并发 5 个请求（全部业务异常）→ 前 2 个进业务方法抛异常（异常计数累积）
                              → 后 3 个被熔断拦截（业务方法零执行，返回"秒杀太火爆"）
10 秒窗口过期 → 半开放行 1 个试探请求 → 业务执行 → 仍异常 → 重新熔断
异常源消除后 → 半开试探成功 → 熔断关闭 → 业务恢复正常下单
```

**业务异常透传**：限购异常返回原文"每人限购1件"（而非笼统的"服务不可用"），业务语义保真。

## 5. 网关令牌桶限流（Redis RequestRateLimiter）

**场景**：网关层对 mall-portal 路由按客户端 IP 限流，20 QPS、桶容量 40。

**结果**：100 并发压测——72 通过、28 拦截（HTTP 429）。令牌桶（burst 40 + 每秒补充 20）在并发突发下正确放行桶容量内的请求、拒绝超出部分。

**结论**：入口限流挡在服务之前，被拒请求不触碰任何业务资源；与 Sentinel 服务层限流形成双层防护（网关管"谁打得太多"，Sentinel 管"单接口扛不扛得住"）。

## 6. RabbitMQ 延时关单 + 消费重试与死信

**毒消息**：向消费队列投递格式非法消息（body 非数字），实测 3 次尝试（2s/4s 退避）后由 RepublishMessageRecoverer 转发至死信队列 `mall.order.cancel.dlq`，死信消息头携带完整异常堆栈；消费队列零积压（无无限 requeue）。

**全链路**：TTL 队列 8 秒过期 → 死信转发 → 消费队列 → 幂等关单（订单不存在时跳过、消息确认）——全部正常。

**结论**：瞬时故障靠重试自愈（幂等保护保证安全）、持续故障进死信留痕，消息链路不会因单条坏消息卡死。

## 7. 可靠消息投递（本地消息表 Outbox）

**正常路径**：admin 上下架商品 → 消息与 DB 同事务落表 → afterCommit 发送 → Broker 确认后 status=1 → search 消费同步 ES（3 秒内 ES 文档删除/恢复）。

**故障路径**：向消息表插入错误交换机记录，定时任务补发两轮后：status=0 保持（不再误标已发送）、retry_count=2（每轮 +1）。

**自愈路径**：修正交换机后，30 秒内下一轮定时任务补发成功 → status=1。

**结论**：消息"落库与业务同生共死 + 确认才记账 + 定时补发"，DB 与 MQ 之间的不一致窗口被消除。

## 8. 登录安全

**失败锁定**：连续 5 次错误密码后，第 6 次正确密码被拒绝（"登录失败次数过多"）；Redis 计数 5、TTL=600s；解锁后正确密码登录成功且计数清零。

**双 token 换发**：登录返回 accessToken + refreshToken；用 refreshToken 换发成功返回新双凭证，新 accessToken 的 Redis TTL=7199 秒（2 小时配置生效）；旧 refreshToken 二次换发被拒（一次性作废防重放）。

## 9. ES 检索增强

**属性筛选**：按规格参数筛选（如系统=Android）结果 total=7，与 ES 原生 nested DSL 查询 count 完全一致；type=0 规格属性筛选命中 0（参数/规格正确区分）。

**聚合联动**：无筛选聚合 8 个品牌/9 种屏幕尺寸；加品牌华为筛选后收缩为 1 个品牌/2 种尺寸——筛选项与商品范围同步。

**上下架同步**：MQ 自动同步链路实测——下架 3 秒后 ES 文档 404、上架 3 秒后恢复 200。
